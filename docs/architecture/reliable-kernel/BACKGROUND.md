# 项目背景

> r4 注记：本文保留历史背景；当前目标合同为 `2026-07-31-r4`，产品决定以 contracts 目录为准。


## 一、LimCode2 现在是什么

LimCode2 是一个运行在 VS Code 里的本地 AI 编程助手。它不再只是聊天窗口，而是在逐步形成一套本地 Agent 运行内核，主要包含：

```text
VS Code 扩展宿主
TypeScript ECS 后端
Vue + Pinia 前端
大模型提供方
工具运行时
主 Agent 与子 Agent
本地持久化与恢复
```

系统已经具备或正在建设这些能力：

- 多轮对话和流式回复；
- 文件读取、修改和审批；
- 命令执行与后台进程；
- 工具结果审核；
- 上下文压缩；
- 子 Agent 并行工作和异步交付；
- 扩展宿主重启后的恢复；
- 中断、重试和并发控制；
- 运行历史与本机重放。

项目尚未正式发布，所以旧的运行时数据没有兼容义务。发现旧模型不合理时，直接切换到新模型，不做双写、旧协议回退或长期迁移链。

## 二、为什么要重写可靠控制面

早期版本主要由 ECS 系统直接推动执行。一个系统改运行状态，另一个系统改消息，工具回调、用户审批和模型回调又各自改一部分数据。

功能少时这种方式很快，功能多以后则出现了明确问题：

- 删除、停止和回调互相抢状态；
- 重试后消息可能消失；
- 执行已经结束，但消息还停在旧状态；
- 工具已经执行，结果却没有可靠落盘；
- 扩展重启后无法判断外部操作到底做没做；
- 子 Agent 和父 Agent 对同一次交付理解不一致；
- 多个系统同时认为自己负责完整生命周期；
- 外部世界已经变化，但会话里的回写失败。

从提交 `4c0c5ff4ad4451725c848879a5dba85d0682fd51` 之后，项目开始系统性重写这部分。当前已经建立：

```text
Turn / TurnIntent / PendingTurnInput
ExecutionLease / AuthoritySnapshot
Operation / Attempt / EffectIntent
RuntimeInbox / RuntimeDelivery
Interaction
AnswerBridge / AnswerSubmission / ChildTurnLink（当前文件后端的旧来源模型）
```

旧的核心生命周期系统已大量删除，执行权威正在从 ECS 迁移到可靠控制面。r4 目标不保留单一 ChildTurnLink，而使用稳定 ChildExecution 及 Parent/Turn/Intent/ActiveTurn 四类独立 Link。

## 三、重写以后又暴露了什么

为了在普通文件上实现可靠性，项目自行实现了：

```text
WAL
Prepared / Committed
HEAD
CAS
Staging
锁与写入代次
崩溃恢复
压缩和完整性校验
```

这能解决一部分可靠性问题，但也让项目开始自己承担数据库的职责。现在最重的几个文件已经达到上千甚至数千行，普通操作也可能反复读取、哈希和重写很大的会话聚合数据。

因此，下一步不是继续给文件数据库打补丁，而是让 SQLite 接管事务、约束、索引和恢复，让业务代码回到 Agent 本身。

## 四、当前确认的三个主要问题

### 4.1 工具执行结果和外部副作用混在一起

当前文件工具大致会经历：

```text
生成修改提案
→ 把提案保存成最终工具结果
→ 等待用户批准
→ 执行真正的文件修改
→ 再保存一个最终工具结果
```

这会让同一个工具调用出现两个“最终结果”，也会混淆提案、执行和模型应该看到的结果。

目前已有临时止血，但最终模型必须改成：

```text
ToolCall
→ ToolExecution
→ Operation
→ EffectIntent
→ EffectReceipt
→ ToolOutcome
→ 唯一 ToolModelResult
```

文件修改提案独立成为 `FileChangeSet`，不再冒充模型结果。

### 4.2 长对话上下文按平方增长

当前每次模型调用都会重复保存完整历史和全部来源关系。对话越长，重复越多。

真实数据中已经观察到：

- 消息正文只有约 2.6 MB；
- 运行时权威文件超过 120 MB；
- 历史上下文投影占据其中大部分；
- 临时落盘目录峰值超过 3 GB；
- 扩展宿主内存约 1.35 GB；
- 普通事务可能耗时 3 到 4 秒；
- 前端一次深拷贝也可能耗时数百毫秒。

最终要改成持久上下文序列：

```text
ContextSegment
ContextSegmentSource
ContextSequenceRoot
ModelContextProjection.rootNodeId
```

历史片段共享保存，只记录本轮新增和新的序列根，不再复制完整前缀。

### 4.3 子 Agent 的交付、展示和控制不是同一套事实

后端的子 Agent 答案通常已经成功提交、送达并被父 Turn 处理，但前端仍可能显示“等待主 Agent 接收”。原因是前端还在通过旧的运行关系猜状态。

同时，用户目前不能方便地终止一个子 Agent 以及它的后代。

最终要分别表达：

- 子 Turn 是否仍在执行；
- 答案是否已提交；
- 答案是否已送达；
- 父 Turn 是否已经处理；
- 终止命令是否已经完成。

控制能力至少保留：

```text
启动子 Agent
发送追加信息
等待结果
列出子 Agent
终止一个子 Agent
终止整个子树
```

## 五、三个问题的共同根因

- 一个对象承担了太多互相独立的事实；
- 重要关系藏在命名和推断逻辑里；
- 每次小修改都重新处理整个会话聚合；
- 外部操作的结果依赖一次会话回调成功才算存在；
- ECS 和前端投影仍在承担部分运行权威。

## 六、已经确定的目标

最终结构是：

```text
一个 limcode.sqlite 热控制面
+ 一个 CAS 冷内容目录
+ EffectIntent / EffectReceipt
+ RuntimeInbox / RuntimeDelivery
+ 持久 ContextSequence
+ ChildExecution + Parent/Turn/Intent/ActiveTurn Links
+ AnswerBridge / AnswerSubmission
+ 有界 ClientState
```

其中：

- SQLite 保存小而需要查询、约束和事务的数据；
- CAS 保存工具原文、文件目标内容、上下文正文、答案正文和差异等大内容；
- Workspace 和模型提供方作为外部世界，通过“意图、执行、回执、核对”管理；
- ECS 只做运行投影；
- 前端只接收当前页面真正需要的有界数据；
- Turn 成为唯一执行身份。

## 七、SQLite 迁移边界

迁移采用一次硬切换：

1. 新实现先在隔离数据根中验证；
2. 停止旧运行时写入；
3. 归档旧的运行时数据；
4. 保留设置、Agent、工作环境和工作区文件；
5. 创建新的 SQLite 数据库和 CAS 目录；
6. 写入当前运行时标识；
7. 重启扩展宿主后启用新内核。

不会做：

- 旧运行时数据导入；
- 新旧双写；
- 自动回退到旧内核；
- 多版本协议协商；
- 一长串历史迁移脚本。

## 八、可靠性的实际边界

系统只承诺它真正能证明的事情：

- 模型最终结果只生成一次；
- 能核验的文件副作用通过哈希判断最终结果；
- 不能查询、也不能安全重试的外部操作，状态记为 `outcome_unknown`，也就是“结果未知”；
- 模型提供方只对明确的临时故障做少量、可见、可取消的重试；
- 文件修改、命令执行和启动子 Agent 不做自动重试。

目标不是把自用插件做成银行系统，而是保证基本能力不丢、状态不说谎、代码还能继续维护。

这些边界在目标形态下的不变量表述以[不变量与权威](./01-invariants-and-authority.md)为准；本节只解释为什么边界定在这里。
