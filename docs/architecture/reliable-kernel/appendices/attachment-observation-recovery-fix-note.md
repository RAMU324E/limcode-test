# 附件分析失败后恢复的保存修复

对应合并请求：第 7 号。修复说明随代码和回归测试一起提交。

## 问题与原因

附件分析失败时，第 7 号请求会生成明确标注“附件尚未分析”的占位结果，让文字压缩继续。
但原来的保存入口也把占位结果写进了可复用附件分析关系（`AttachmentObservationLink`）。
同一附件、同一分析配置只允许保存一份不可变的成功分析结果。后续分析恢复后，新的内容与占位内容不同，数据库检查便会拒绝第二次压缩。

修复前，新增测试通过实际模型适配器处理模拟响应，再使用临时数据库连续执行“失败、失败、恢复”，在恢复结果写入时重现了关系记录检查失败。

## 修改范围

- 在 `backend/reliableKernel/attachmentObservations.ts` 统一维护尚未分析结果的标记与判断。
- 准备可复用分析记录之前，完整检查附件编号、数量、重复项、缺失项和内容格式。尚未分析的结果只留在当次压缩摘要中，不生成可复用分析关系。
- 在保存文档的编码入口再次拒绝尚未分析的结果，避免其他调用直接把占位内容存入成功分析记录。
- `backend/capabilities/llmProvider.ts` 复用上述判断，后续遇到未成功分析的附件仍可再次尝试。
- 保留第 5 号请求的附件解析与有界重试修复，以及第 7 号请求的断线重试改动。

## 数据保留

- 不改数据库表、索引、运行数据格式标识或配置格式，不清空、重置、迁移已有数据。
- 原附件的内容与信息保持不变，失败时也不丢弃原附件。
- 当次摘要继续明确说明附件没有分析成功；以后分析成功，不会回写或改造旧摘要。
- 成功分析首次保存后可以复用；重复提交同一次压缩，不新增重复记录。
- 不覆盖任何已有的成功分析记录，也不为未合并分支引入旧占位数据的迁移。

## 回归验证

新增的三项测试在修复前均失败，覆盖以下检查：

- 失败占位保留在模型可见摘要中，但不进入可复用分析记录；成功与失败混合时只保存成功项，错误身份与格式仍被拒绝。
- 直接构造尚未分析的保存文档也会被拒绝。
- 模型适配器与临时数据库串联执行连续两次失败、恢复成功、成功结果复用；验证旧摘要、原附件内容和信息不变，以及各次压缩可重复提交。

涉及附件保存、附件压缩、模型适配、断线重试和工具不重复执行的六个测试文件已通过，共 99 项。
新增测试位于 `tests/reliable-kernel/attachment-catalog-projection.test.mjs`，该文件已被项目本地测试与远端自动检查收录。

完整检查命令为 `npm run check:local`；合并前还应执行 `node scripts/reliable-kernel/check-plan.mjs --require-tracked`，并确认合并请求及主分支的远端检查结果。

## 已落盘占位缓存的失效

此前修复禁止新占位结果进入成功分析缓存，但遗漏了分析合同版本更新。已经存在的占位关系仍与新分析共用同一缓存键，读取时会被成功分析文档校验拒绝，导致压缩在请求模型之前失败；重复请求不能消除这一确定性错误。

将现有 `ATTACHMENT_OBSERVATION_PROMPT_REVISION` 更新为 `2026-09-07`，使缓存键中已有的合同版本维度随“仅成功观察可复用”的语义一起更新。不放宽文档校验，不覆盖不可变关系，不修改数据库结构、旧摘要、原附件或用户配置，也不引入旧格式读取与迁移。

旧合同下的附件分析缓存不再复用，升级后的首次相关压缩可能需要重新分析附件；新合同下的成功结果继续正常缓存与复用。若分析仍不可用，占位结果只进入当次摘要，不会再次堵塞后续恢复。

新增回归直接在临时数据库中保留旧合同的占位关系，覆盖继续压缩、再次分析不可用、成功恢复、成功缓存复用及幂等提交；同时核对旧关系、旧摘要和附件内容不变。修复前该回归复现 `Unavailable attachment observations cannot be cached.`，不是通过删除测试数据来绕过问题。
