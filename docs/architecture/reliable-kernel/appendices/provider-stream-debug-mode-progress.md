## 本轮实现与验证

- `debugCapture/files.ts` 将原文先同步，再同步索引，最后原子发布清单；只有发布成功才更新内存中的可靠截止点。队列、写入中的数据及编码临时空间有预算检查。
- 单次 8、16、32 兆均通过实际写入到限测试；到限只停止取证。30 分钟上限由单调时钟控制；累计空间和份数不足时拒绝开启。
- 普通连接在依赖库真实拆分、解码和参数组装位置建立来源引用；长连接在原始消息解析前记录，保留实际选中工具和选择依据。
- 界面记录实际追加、替换、完成和快照重建。每批最多 128 千字节、待发缓存最多 256 千字节；缺确认或超限明确标记缺口，不影响显示与模型执行。
- 分析器只读有限前缀并核验原文字节摘要，区分入口重复、本地重复、错误归属、等长内容变更、完成遗漏和无法确定的情况。
- 现场使用三个独立文件，不进入聊天数据库；没有更改数据库表、运行期号、模型执行、重试或原有基础日志规则。
- 完整本地检查通过：365 项中 352 通过、13 跳过、0 失败；构建、界面类型检查、11 份合同检查通过。该结果属于未提交工作区，不冒充干净提交或远端验证。
- 已通过二十万以上未闭合参数重建、真实连接自动切换、两工具交错思考、同源重复与错配、等长变更、损坏文件、旧命令重放和读取时禁止删除测试。
- 已启动独立子进程，分别在原文、索引和清单同步后强制结束，再用新实例只读核验有效前缀；重启不自动恢复取证。
- 真实浏览器已检查 1440、390、320 像素宽度，未发现横向溢出或按钮越界；已验证设置保存、启停、分析和删除确认。界面使用模拟宿主，不把它当作编辑器安装验证。

## 使用与证据边界

1. 调试原文在当前运行目录下的 `diagnostics/debug-captures/`，不是数据库新增表。设置页可对停止后的记录打开目录、导出、分析或删除。
2. 中途开启只能记录之后收到的内容；本地已有参数作为单独起点保存。来源未关联、界面停止边界未回传或异常退出均不能假称完整。
3. 原始字节和各层实际处理值均保留；每层使用增量片段，只有起点、替换和最终结果可能保存累计值，不逐片段重写累计全文。
4. 4 兆是取证队列、写入中数据和编码预留的预算，不是整个编辑器或模型业务进程的内存上限。
5. 原文可能包含请求、思考、参数和错误正文。开启即保存，不另设内容筛选开关；不采集认证请求头，不自动上传或覆盖现场。
6. 此功能用于定位下次故障，并没有宣称已经确定或修复历史那次无限参数增长的根因。

## 第 2 阶段发现

### 当前依赖的证据

依赖锁定为 `unified-llm-provider` 0.1.35，以下结论仅针对本次读取的已安装代码，不冒充其他版本现状。

| 证据 | 位置 | 结论 |
| --- | --- | --- |
| 调试接口仅有请求、响应和读取块回调 | `node_modules/unified-llm-provider/dist/config/types.d.ts` 的 `LLMDebugHooks` | 没有实际事件拆分序号、事件对应的原始字节范围或解码来源引用 |
| 现成调试实现需要响应回调才能启用逐块回调 | `node_modules/unified-llm-provider/dist/llm/transport.js` 的 `wrapStreamForDebug` | 不能只接一个逐块回调就认为已开始取证 |
| 现成调试实现保留所有片段并反复拼累计全文 | 同上 | 不能直接用于原方案的有界增量保存 |
| 实际事件拆分发生在库内 `parseSSE` | `node_modules/unified-llm-provider/dist/llm/response.js` | 解码回调能看到实际输入，但看不到它来自哪一次拆分及哪些输入字节 |
| 项目掌握长连接原始接收与参数组装 | `backend/capabilities/openAIResponsesWebSocketSession.ts` | 长连接可直接加窄观察接口；当前尚未接入 |

### 模拟验证

`tests/reliable-kernel/debug-capture-provenance.test.mjs` 使用当前依赖的公开函数与假网络响应，不连接真实模型：

1. 仅设置逐块调试回调，回调次数为零。
2. 同时设置响应回调后，每次逐块回调都带累计全文，字段没有来源身份或字节范围。
3. 同一次读取提供两条内容完全相同的事件，实际解码发生两次，二者都对应同一次读取，解码输入也相同。

第三项说明读取块编号不等于消息编号。仅按时间、读取次数或相同文字匹配，不能作为原方案要求的精确来源关系；这些模拟也不证明历史故障由依赖库导致。

## 已确认的补充范围

建议先给统一模型接入库补充公开的、仅观察的接口，再继续原方案：

1. 在实际读取原始字节、实际拆出事件、实际解码完成这三个位置传出明确编号和来源关系，而不是由外层重新猜测。
2. 多块拼成一个事件、一个块拆成多个事件、解析失败、上游错误、完成事件和读取中断都必须可对应；内容相同的两次输入仍有独立身份。
3. 接口支持运行中开启；关闭时不建立详细记录队列、不拼累计全文，观察回调失败不能改变模型结果。
4. 不改变现有解析结果、工具判断、请求内容或重试行为；用固定输入比较开启与关闭前后的输出和执行次数。
5. 在依赖的源码层完成并固定可核验的构建来源，不临时修改 `node_modules` 私有字段，不扩大为整个依赖库重构。

用户已明确同意上述依赖库接口与锁定构建的维护范围。现有容量、时限、默认关闭、原文不额外筛选的决定不变。
